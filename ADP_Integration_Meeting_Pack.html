1. Purpose & Integration Overview

The AGC University Member Portal currently manages employee data independently in its own database. This integration will connect the portal directly to ADP Workforce Now as the authoritative source of truth for:

  • Employee general information (names, titles, departments, work locations)
  • Reporting hierarchy (manager-to-report relationships for dynamic org charts)
  • Vacation & time-off balances and approved requests

Rather than duplicating and manually maintaining employee records, the portal will query ADP's API, ensuring data is always current and eliminating double-entry errors.

Auth methodOAuth 2.0 with certificate-based client authentication (mTLS)

3. How the Data Will Be Used in the Portal

3.1 People Directory & Profile Cards

The employee search and profile pages will switch from the portal's own user table to live ADP data. When a user searches for a colleague, the portal queries ADP's worker list (filtered to active employees) and displays name, title, department, facility, and photo.

3.2 Org Chart Auto-Population

Instead of maintaining static JSX files per facility, the org chart will be driven by the reportsTo hierarchy from ADP. Each node renders using the same OrgPersonNode component already in the codebase, populated at runtime rather than hardcoded. Manual overrides per node are still supported for cases where ADP data doesn't match the intended display (e.g. consultants, dual-reporting).

3.3 Vacation Dashboard Widget

A new widget on the employee's home dashboard will show:

  • Remaining vacation balance (in hours or days — configurable)
  • Next approved time-off block (start date, end date, duration)
  • Any pending requests awaiting approval, clearly labelled as Pending

3.4 Manager View — Team Absence Overview

Managers will see a summary card listing direct reports who are on approved leave this week or this month, helping with scheduling and coverage planning. This uses the reportsTo field to identify direct reports, combined with the time-off request data.

3.5 Data Sync Strategy

Two-layer approach
  • Live API call — used for searches, profile views, and org chart loads; always fresh
  • Triggered on user navigation; cached in memory for the session duration
  • Daily background sync — runs nightly via a scheduled job on the portal backend
  • Caches ADP data to a local sync table for fast dashboard loads and offline fallback
  • Sends an internal notification if any employee's title, department, or manager changed

4. Technical: Certificate-Based OAuth 2.0 Flow

ADP's API uses OAuth 2.0 with mutual TLS (mTLS). The portal backend authenticates by presenting a client certificate signed by ADP's Certificate Authority. The private key never leaves the server.

Authentication sequence
  1. IT generates a 2048-bit RSA private key — stored securely on the server, never committed to the repository
  2. IT generates a Certificate Signing Request (CSR) using the private key
  3. Only the CSR (.csr file) is sent to ADP — the private key stays internal
  4. ADP signs the CSR and returns a certificate (.crt / .pem)
  5. The portal backend loads both the private key and the ADP-issued certificate at runtime from environment variables or a secrets vault
  6. For each API call: the backend uses the certificate to obtain a short-lived OAuth 2.0 access token from ADP's token endpoint
  7. The access token is used to authenticate API requests; it expires and is renewed automatically

5. Day 6 — CSR Generation: Step-by-Step (IT)

On Day 6, IT generates the private key and CSR. These commands run on the server or a secure workstation. The private key must never be shared, emailed, or committed to source control.

Step 1 — Generate the private key

Run the following command to create a 2048-bit RSA private key:

openssl genrsa -out agc-portal-adp.key 2048
Keep agc-portal-adp.key on a secure machine or in a secrets vault (e.g. AWS Secrets Manager, Azure Key Vault, Render environment variables). Do NOT share it, email it, or push it to git.

Step 2 — Generate the CSR

Use the private key to create the Certificate Signing Request. You will be prompted to fill in the Distinguished Name fields:

openssl req -new -key agc-portal-adp.key -out agc-portal-adp.csr

When prompted, enter:

Prompt FieldValue to Enter
Country Name (C)CA
State or Province (ST)Your province (e.g. Ontario)
Locality (L)Your city (e.g. Mississauga)
Organisation Name (O)AGC University Inc. (or your legal entity name)
Organisational Unit (OU)IT / Portal Development
Common Name (CN)portal.agcuniversity.com (or your registered domain)
Email AddressIT contact email address
Challenge password(leave blank — press Enter)

Step 3 — Verify the CSR (optional but recommended)

openssl req -noout -text -in agc-portal-adp.csr

Confirm that the Subject fields match what you entered, and that the Public Key algorithm shows RSA (2048 bit).

Step 4 — Send the CSR to ADP

  • Attach agc-portal-adp.csr to the ADP submission portal or email it to your ADP Implementation contact
  • Do NOT attach the .key file — only the .csr file goes to ADP
  • ADP will process the CSR and return a signed certificate (.crt or .pem file), typically within a few business days

Step 5 — Store the returned certificate securely

Once ADP returns the signed certificate:

  • Store both agc-portal-adp.key and the returned agc-portal-adp.crt in a secrets vault or as encrypted environment variables on Render
  • On the portal backend, load them at runtime via:
ADP_CLIENT_KEY=<contents of .key file> ADP_CLIENT_CERT=<contents of .crt file>
  • Rotate the certificate before it expires (ADP will specify the validity period — typically 1–2 years)
  • Add *.key and *.crt to .gitignore as a precaution

7. Security Checklist

Before Day 6 — CSR submission
  • Confirm the key-generation machine is secure and not shared
  • Ensure the secrets vault (or Render environment) is ready to receive the key + cert
  • Add *.key and *.crt to .gitignore in the portal repository
After receiving the ADP certificate
  • Load ADP_CLIENT_KEY and ADP_CLIENT_CERT as environment variables on Render — never in code
  • Restrict the ADP API scope to read-only (worker data, time-off) — do not request write permissions
  • Log all ADP API calls on the backend without logging token values
  • Set up certificate expiry alerts at 60-day and 30-day marks
  • Do not cache access tokens beyond their expiry time
